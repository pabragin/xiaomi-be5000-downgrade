# Xiaomi BE5000 (RD18): раздача штатной прошивки 1.0.53 по Ethernet

Этот репозиторий содержит DHCP/TFTP-сервер для **macOS**. Он передаёт официальную
подписанную прошивку Xiaomi загрузчику RD18 в режиме восстановления. Скрипт
сам не записывает флеш-память и **не обходит проверку отката**: получение 100%
по TFTP ещё не доказывает, что версия изменилась. На другом экземпляре или
версии загрузчика результат может отличаться.

## Файлы

- `recover.py` — сервер DHCP/TFTP, который обслуживает только один клиент
  восстановления и только образ 1.0.53.
- `POST.md` — краткий отчёт о реальном откате с 1.0.91.
- Образ прошивки не включён. Загрузите его напрямую с сервера Xiaomi:
  <https://cdn.cnbj1.fds.api.mi-img.com/xiaoqiang/rom/rd18/miwifi_rd18_firmware_6c571_1.0.53.bin>

Размер образа: `31 069 192` байта. SHA-256:
`cdc567abd5b9d4ff10adb02ee9592575640e5607135a4588f05e7bdc2cab17d0`.
Скрипт сверяет оба значения до открытия серверов.

## Подготовка Mac

1. Узнайте имя проводного интерфейса: `networksetup -listallhardwareports`.
   Например, у автора USB-Ethernet адаптер имел имя `en8`.
2. Соедините Mac кабелем напрямую с **первым Ethernet-портом RD18 (LAN1)** —
   именно он использовался при успешной попытке. Отключите WAN и остальные
   устройства от роутера. Не используйте Wi-Fi для этого способа.
3. Убедитесь, что системные DHCP/TFTP-службы не занимают UDP-порты 67 и 69:
   `sudo lsof -nP -iUDP:67 -iUDP:69`. Если заняты, выключите «Общий интернет»
   или другую службу, использующую порт, и повторите проверку.
4. Поместите файл прошивки рядом с `recover.py` и проверьте хеш:

   ```sh
   cd /путь/к/be5000-rd18-recovery
   curl -fL -o miwifi_rd18_firmware_6c571_1.0.53.bin 'https://cdn.cnbj1.fds.api.mi-img.com/xiaoqiang/rom/rd18/miwifi_rd18_firmware_6c571_1.0.53.bin'
   shasum -a 256 miwifi_rd18_firmware_6c571_1.0.53.bin
   ```

## Режим восстановления

1. Запустите сервер, подставив свой Ethernet-интерфейс:

   ```sh
   sudo /usr/bin/python3 recover.py --interface en8
   ```

2. Дождитесь строк `TFTP listening` и `DHCP listening`.
3. Отключите питание RD18. Удерживая Reset, включите питание. Отпустите Reset,
   когда индикатор начнёт мигать жёлтым. Дождитесь `DHCP DISCOVER`, `TFTP RRQ`
   и прогресса до 100%. Повторные DHCP-запросы без завершённой передачи
   означают, что образ не получен целиком.
4. После `TFTP transfer complete` обычно нужно оставить роутер включённым и
   дождаться его реакции: передача файла ещё не означает успешную запись.
   Особенности нашего случая с погасшим индикатором описаны ниже.
5. После загрузки проверьте версию в веб-интерфейсе или через локальный API:

   ```sh
   curl -fsS 'http://192.168.31.1/cgi-bin/luci/api/xqsystem/init_info'
   ```

   Нужные поля: `hardware` должно быть `RD18`, `romversion` — `1.0.53`.
6. Завершите сервер `Ctrl+C`. Он удалит добавленный им адрес
   `192.168.31.100/24` с интерфейса Mac.

Скрипт автоматически распознаёт загрузчик по DHCP-полю `tclinux.bin` и
запоминает его MAC-адрес. При необходимости его можно задать явно через
`--router-mac 00:11:22:33:44:55`, но используйте MAC из пакета загрузчика,
а не адрес другого устройства.

## Что произошло при откате с 1.0.91

При первой передаче TFTP дошёл до 100%, но версия 1.0.91 сохранилась.
В следующих попытках роутер **полностью получал образ по TFTP**, а индикатор
после передачи оставался выключенным. В нашем случае в этом состоянии
несколько раз отключали питание: ориентировочно через 10 секунд после
завершения TFTP, затем при очередной попытке — примерно через 20 секунд.
После этого снова запустили восстановление с зажатым Reset и образом 1.0.53,
дали роутеру загрузиться и проверили: API показал `romversion: 1.0.53`.

Это наблюдение, а не проверенная процедура: точное число попыток и моменты
отключения не фиксировались. Погасший индикатор **не позволяет определить**,
проверяет ли роутер образ или записывает его во флеш. Намеренное отключение
питания даже после окончания TFTP может оставить роутер без загрузки; для
ремонта может потребоваться UART или программатор. Один только лог `100%`
не подтверждает откат.
